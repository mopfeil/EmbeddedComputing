\section{Processors for Embedded Systems}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\nsl{Embedded systems use a wide range of processors, from 8 bit
microcontrollers that cost a few cents to multi-core application processors
that run Linux. The choice depends on the computing power needed, on the
memory, on the peripherals, on the energy budget and, in large series, on
the price. This chapter first describes the classes of processors and the
basic architecture concepts. Then it looks at the families used in this
lecture: the 8 bit AVR of the Arduino Uno, the ARM Cortex-M0+ of the
Raspberry Pi Pico and the RISC-V core of the ESP32-C3. All three can be
simulated in Wokwi.
\newpage}

\begin{description}
\item[{\rot\bf Classes of processors}]~\\[-\lblskip]
\bi
	\ite \textbf{microcontroller} (MCU): CPU, flash, RAM and peripherals on one chip
	\bi
		\ite runs without an operating system or with an RTOS; starts in milliseconds; consumes milliwatts or less
		\ite 8 bit (AVR, PIC, 8051) for very simple, cheap devices; 32 bit (ARM Cortex-M, RISC-V) for almost everything else
	\ei
	\ite \textbf{application processor} (MPU): fast cores with memory management unit, external DRAM, usually Linux or Android
	\bi
		\ite ARM Cortex-A (smartphones, Raspberry Pi), increasingly RISC-V application cores
	\ei
	\ite \textbf{digital signal processor} (DSP): optimised for filter and transformation algorithms (audio, radio, motor control)
	\ite \textbf{FPGA}: configurable logic, for highly parallel or very fast functions; often combined with processor cores (system on chip)
	\ite modern chips combine several of these: e.g.\ Cortex-A cores for Linux plus a Cortex-M core for real time on the same die
\ei
\os{\newpage}

\item[{\rot\bf Processors of this lecture (all simulated in Wokwi)}]~\\[-\lblskip]
\begin{center}
\resizebox{\textwidth}{!}{%
\begin{tabular}{|l|c|c|c|c|}
\hline

\hline

architecture & AVR, 8 bit & ARM Cortex-M0+, 32 bit & RISC-V RV32IMC, 32 bit & ARM Cortex-M3, 32 bit \\

\hline

\end{center}
\bi
	\ite the successor of the RP2040, the RP2350 (Raspberry Pi Pico 2), offers two Cortex-M33 \textbf{or} two RISC-V cores on the same chip -- selectable at boot
\ei
\os{\newpage}

\item[{\rot\bf Von Neumann and Harvard architecture}]~\\[-\lblskip]
\begin{figure}[!hbtp]
\begin{center}
\resizebox{0.8\textwidth}{!}{%
\begin{tikzpicture}[font=\sffamily\small,>=Stealth,
	b/.style={draw,thick,minimum width=22mm,minimum height=10mm,align=center}]

	\node[b,fill=gray!10] (m1) at (3,0) {memory\\code + data};
	\draw[<->,very thick] (c1) -- node[above,font=\sffamily\scriptsize]{one bus} (m1);
	\node[above] at (8.5,1.6) {\textbf{Harvard}};
	\node[b,fill=rwucyan!10] (c2) at (8.5,0) {CPU};
	\node[b,fill=gray!10] (m2) at (6,0) {code\\memory};
	\node[b,fill=gray!10] (m3) at (11,0) {data\\memory};
	\draw[<->,very thick] (c2) -- node[above,font=\sffamily\scriptsize]{instr.} (m2);

\end{tikzpicture}}
\caption{One bus for code and data, or separate buses}
\end{center}
\end{figure}
\bi
	\ite \textbf{Harvard}: fetching the next instruction and accessing data at the same time -- higher throughput
	\bi
		\ite AVR: pure Harvard; constants in flash need special instructions (\texttt{PROGMEM}, \texttt{lpm})
	\ei
	\ite \textbf{modified Harvard} (Cortex-M, RISC-V MCUs): separate instruction and data buses or caches, but \textbf{one} common address space -- a pointer can point to flash or RAM
\ei
\os{\newpage}

\item[{\rot\bf RISC and CISC}]~\\[-\lblskip]
\bi
	\ite \textbf{CISC} (complex instruction set computer, e.g.\ x86): many instructions, memory operands in arithmetic instructions, variable length
	\ite \textbf{RISC} (reduced instruction set computer): all microcontroller architectures of this lecture
	\bi
		\ite \textbf{load/store architecture}: arithmetic only on registers; memory accessed only with load and store
		\ite many general purpose registers (AVR 32 $\times$ 8 bit, Cortex-M 13 $\times$ 32 bit + SP, LR, PC, RISC-V 31 $\times$ 32 bit + zero register)
		\ite simple, mostly fixed length instructions $\Rightarrow$ easy to decode and to pipeline
		\ite compressed instruction sets for small code: ARM Thumb (16 bit), RISC-V ``C'' extension
	\ei
	\ite \textbf{pipeline}: fetch, decode, execute overlap -- ideally one instruction per clock
	\bi
		\ite Cortex-M0+: 2 stages; Cortex-M3/M4: 3 stages; Cortex-M7: 6 stages, two instructions per clock
		\ite a jump empties the pipeline: branches cost extra cycles
	\ei
\ei
\os{\newpage}

\item[{\rot\bf The same C function on four processors}]~\\[-\lstskip]
\begin{lstlisting}[language=C]
uint32_t sum(const uint16_t *a, int n) {
    uint32_t s = 0;
    for (int i = 0; i < n; i++) {
        s += a[i];
    }
    return s;
}
\end{lstlisting}
\begin{center}
\resizebox{0.85\textwidth}{!}{%
\begin{tabular}{|l|c|c|l|}
\hline
\textbf{processor} & \textbf{instructions in the loop} & \textbf{code size} & \textbf{reason} \\
\hline
AVR (8 bit) & 12 & 40 bytes & 32 bit sum and 16 bit index need several 8 bit operations \\
Cortex-M0+ & 7 & 24 bytes & 16 bit Thumb instructions \\
Cortex-M4 & 6 & 24 bytes & load with scaled index: \texttt{ldrh r4, [r0, r3, lsl \#1]} \\
RISC-V RV32IMC & 7 & 28 bytes & mix of 16 and 32 bit instructions \\
\hline
\end{tabular}}
\end{center}
\bi
	\ite compiled with \texttt{-Os} (optimise for size); listings and script in \texttt{examples/processors}, or try it on \url{https://godbolt.org}
\ei
\os{\newpage}

\item[{\rot\bf The loop in assembly: AVR and Cortex-M0+}]~\\[-\lstskip]
\begin{lstlisting}[language={}]
; AVR: s in r22..r25 (4 x 8 bit), pointer in Z (r31:r30), i in r19:r18
.L3:  ld   r26,Z+            ; low byte of a[i], Z++
      ld   r27,Z+            ; high byte of a[i], Z++
      add  r22,r26           ; s += a[i], byte by byte with carry
      adc  r23,r27
      adc  r24,__zero_reg__
      adc  r25,__zero_reg__
      subi r18,-1            ; i++ (16 bit)
      sbci r19,-1
.L2:  cp   r18,r20           ; i < n ?
      cpc  r19,r21
      brlt .L3
\end{lstlisting}
\begin{lstlisting}[language={}]
@ Cortex-M0+: a in r0, n in r1, i in r3, s in r2
.L3:  lsls  r4, r3, #1       @ byte offset = i * 2
      ldrh  r4, [r0, r4]     @ load halfword a[i]
      adds  r3, r3, #1       @ i++
      adds  r2, r2, r4       @ s += a[i]
      b     .L2
.L2:  cmp   r3, r1           @ i < n ?
      blt   .L3
\end{lstlisting}
\os{\newpage}

\item[{\rot\bf The loop in assembly: RISC-V}]~\\[-\lstskip]
\begin{lstlisting}[language={}]
# RISC-V: a in a4 (copied from a0), n in a1, i in a5, s in a0 (= return value)
.L2:  blt   a5,a1,.L3        # i < n ? compare and branch in one instruction
      ret
.L3:  slli  a3,a5,1          # byte offset = i * 2
      add   a3,a4,a3         # address = a + offset
      lhu   a3,0(a3)         # load halfword unsigned
      addi  a5,a5,1          # i++
      add   a0,a0,a3         # s += a[i]
      j     .L2
\end{lstlisting}
\bi
	\ite RISC-V has no status flags: compare and branch are one instruction (\texttt{blt})
	\ite only one addressing mode (register + 12 bit offset) -- the address is computed with normal instructions
	\ite register names of the calling convention: \texttt{a0}--\texttt{a7} arguments and return values, \texttt{sp} stack pointer, \texttt{ra} return address, \texttt{zero} always 0
	\ite more about assembly programming in chapter Programming
\ei
\os{\newpage}
\end{description}

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\section{Microcontroller Families}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\nsl{Most new designs today use one of two 32 bit architectures: ARM
Cortex-M, licensed by Arm to almost every semiconductor company, or RISC-V,
an open instruction set that anybody may implement without license fees.
8 bit microcontrollers are still produced in huge numbers for very simple
and cost-sensitive devices. Because the cores are similar, the differences
between microcontrollers are mostly in the peripherals, the memory, the
power consumption and the software support.}

\begin{description}
\item[{\rot\bf 8 bit AVR (ATmega328P)}]~\\[-\lblskip]
\bi
	\ite 32 registers of 8 bit, most instructions in one clock cycle, 16\,MHz on the Arduino Uno
	\ite pure Harvard architecture: 32\,KB flash for code, 2\,KB SRAM for data, 1\,KB EEPROM
	\ite 5\,V operation, robust I/O pins, very low sleep current (well below 1\,$\mu$A in power-down)
	\ite limits: 16 or 32 bit arithmetic needs several instructions, no hardware division, little RAM
	\ite still used for simple control tasks; and it made embedded programming popular through Arduino
\ei
\os{\newpage}

\item[{\rot\bf ARM Cortex-M}]~\\[-\lblskip]
\bi
	\ite Arm designs the cores and licenses them; the chip manufacturers (ST, NXP, Raspberry Pi, Nordic, \ldots) add memory and peripherals
	\ite the same core, the same tools and the same interrupt controller across thousands of chips
\ei
\begin{center}
\resizebox{\textwidth}{!}{%
\begin{tabular}{|l|l|l|}
\hline
\textbf{core} & \textbf{architecture} & \textbf{features} \\
\hline
Cortex-M0 / M0+ & ARMv6-M & smallest and most efficient; Thumb subset, no division instruction \\
Cortex-M3 & ARMv7-M & full Thumb-2 instruction set, hardware division \\
Cortex-M4 & ARMv7E-M & + DSP instructions (SIMD, MAC), optional single precision FPU \\
Cortex-M7 & ARMv7E-M & superscalar, caches, optional double precision FPU, up to about 1\,GHz \\
Cortex-M23 / M33 & ARMv8-M & + TrustZone security extension (M33 also DSP and FPU) \\
Cortex-M55 / M85 & ARMv8.1-M & + Helium vector extension for signal processing and machine learning \\
\hline
\end{tabular}}
\end{center}
\bi
	\ite common to all: NVIC interrupt controller, SysTick timer, vector table, debug via SWD
\ei
\os{\newpage}

\item[{\rot\bf RISC-V}]~\\[-\lblskip]
\bi
	\ite open instruction set architecture (since 2010, UC Berkeley; today RISC-V International) -- no license fees
	\ite modular: a small base set plus standard extensions
	\bi
		\ite \textbf{RV32I}: 32 bit integer base, 32 registers (\texttt{x0} is always 0)
		\ite \textbf{M} multiplication/division, \textbf{A} atomic operations, \textbf{F}/\textbf{D} floating point, \textbf{C} compressed 16 bit instructions, \textbf{V} vectors
		\ite ESP32-C3 = RV32IMC
	\ei
	\ite many implementations: commercial (SiFive, Andes, Espressif) and open source (e.g.\ the Hazard3 cores in the RP2350)
	\ite the same compilers (GCC, LLVM) and the same Rust targets as for ARM
	\ite peripherals and interrupt controllers are not standardised as uniformly as on Cortex-M yet
\ei
\os{\newpage}

\item[{\rot\bf Other architectures}]~\\[-\lblskip]
\bi
	\ite \textbf{Xtensa} (Cadence): configurable cores in the ESP32 and ESP32-S3; Espressif's newer chips use RISC-V
	\ite \textbf{PIC}, \textbf{8051}: 8 bit, still common in cost-sensitive mass products
	\ite \textbf{MSP430}: 16 bit, extremely low power (metering, sensors)
	\ite manufacturer-specific automotive cores (e.g.\ Infineon TriCore, Renesas RH850): safety features such as cores running in lock-step
\ei
\os{\newpage}
\end{description}

\section{Inside a Microcontroller}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\nsl{The processor core is only a small part of a microcontroller. Around it
are memories of different kinds, a bus system that connects the core with
the peripherals, a clock system and a power management unit. How these parts
work determines how fast a program really runs, how exactly its timing can
be predicted and how long a battery lasts.}

\begin{description}
\item[{\rot\bf Block diagram of a microcontroller}]~\\[-\lblskip]

\bi
	\ite the bus matrix lets the CPU and the DMA access different memories at the same time
\ei
\os{\newpage}

\item[{\rot\bf Memories}]~\\[-\lblskip]
\bi
	\ite \textbf{flash}: non-volatile program memory; erased in blocks, limited number of write cycles (typically 10\,000--100\,000)
	\bi
		\ite at high clock rates flash is too slow $\Rightarrow$ wait states, prefetch buffers or a cache
		\ite RP2040 and ESP32 execute code directly from an external QSPI flash through a cache (``execute in place'', XIP) -- a cache miss costs many cycles
	\ei
	\ite \textbf{SRAM}: fast, volatile working memory for data, stack and time-critical code
	\ite \textbf{EEPROM} or flash emulation: small, byte-wise changeable non-volatile data (settings, calibration)
	\ite caches make programs faster on average, but timing less predictable $\Rightarrow$ put real-time critical code into RAM (e.g.\ \texttt{IRAM\_ATTR} on the ESP32, \texttt{\_\_not\_in\_flash\_func} on the RP2040)
	\ite \textbf{MPU} (memory protection unit): protects memory regions (e.g.\ catches stack overflows); an MMU with virtual memory exists only on application processors
\ei
\os{\newpage}

\item[{\rot\bf Memory map of the RP2040}]~\\[-\lblskip]
\begin{center}
\resizebox{0.9\textwidth}{!}{%
\begin{tabular}{|l|l|}
\hline
\textbf{address} & \textbf{content} \\
\hline
0x0000\,0000 & boot ROM (16\,KB) \\
0x1000\,0000 & external flash via XIP cache (code, constants) \\
0x2000\,0000 & SRAM (264\,KB: data, stack, heap) \\
0x4000\,0000 & peripherals on the APB bus (UART, SPI, I2C, ADC, PWM, timer, \ldots) \\
0x5000\,0000 & peripherals on the AHB bus (DMA, USB, PIO) \\
0xd000\,0000 & SIO: single-cycle I/O (GPIO, hardware divider, spinlocks) \\
0xe000\,0000 & Cortex-M0+ internal registers (NVIC, SysTick) \\
\hline
\end{tabular}}
\end{center}
\bi
	\ite one 32 bit address space for everything: memory-mapped I/O (see chapter Peripherals and Interfaces)
	\ite the linker places code and data into these regions according to the linker script (\texttt{memory.x} in our Rust examples)
\ei
\os{\newpage}

\item[{\rot\bf Interrupts and exceptions}]~\\[-\lblskip]
\bi
	\ite the \textbf{vector table} at the start of the program contains the initial stack pointer and the addresses of all handlers (reset, faults, interrupts)
	\ite Cortex-M: the hardware saves 8 registers on the stack before the handler starts, so a handler is an ordinary C or Rust function
	\ite interrupt latency: 15 clock cycles on the Cortex-M0+, 12 on the Cortex-M3/M4
	\ite \textbf{NVIC}: priorities, nesting, and \textbf{tail chaining} -- a pending interrupt starts directly after the current one without restoring and saving the registers again
	\ite \textbf{faults} (HardFault, MemManage, BusFault, UsageFault): invalid memory accesses, undefined instructions, division by zero -- the fault handler is the place to log the error and reset
	\ite RISC-V: similar concepts, but the interrupt controller depends on the implementation (CLIC, PLIC or vendor-specific)
\ei
\os{\newpage}

\item[{\rot\bf Clock and power}]~\\[-\lblskip]
\bi
	\ite clock sources: internal RC oscillator (fast start, inaccurate), external crystal (accurate), PLL to multiply the frequency
	\ite dynamic power $P \approx C \cdot U^2 \cdot f$: lower voltage and frequency save energy
	\ite peripherals that are not used should have their clock switched off (clock gating)
	\ite sleep modes: from ``CPU stopped, peripherals running'' to ``everything off except a wake-up timer''
	\bi
		\ite ESP32-C3 deep sleep: about 5\,$\mu$A; Wi-Fi transmission: well above 100\,mA
		\ite a battery device spends most of its time sleeping: average current = sum of (current $\times$ time share)
	\ei
	\ite example: 2000\,mAh battery, 10\,$\mu$A sleep and 1 second at 100\,mA every 10 minutes $\Rightarrow$ average $\approx 0.18$\,mA $\Rightarrow$ about 15 months
\ei
\os{\newpage}

\item[{\rot\bf Arithmetic: integer, fixed point, floating point}]~\\[-\lblskip]
\bi
	\ite without FPU (AVR, Cortex-M0+, ESP32-C3), floating point is done in software: tens to hundreds of cycles per operation
	\ite \textbf{fixed point}: integers with an implied scale, e.g.\ Q15 = value $\times 2^{15}$ in 16 bit
	\bi
		\ite fast on every processor, but the programmer must watch range and rounding
	\ei
	\ite FPU (Cortex-M4F, M7, M33, ESP32-S3): single precision float in one or a few cycles -- \texttt{double} is still done in software if the FPU is single precision only
	\ite \textbf{DSP features}: multiply-accumulate (MAC) in one cycle, saturating arithmetic, SIMD (two 16 bit or four 8 bit operations in one 32 bit instruction)
	\ite dedicated DSPs add zero-overhead loops, circular addressing and several MAC units (VLIW) -- today often replaced by Cortex-M4/M7 or vector extensions
\ei
\os{\newpage}
\end{description}

\section{Application Processors and Selection}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\nsl{When an application needs a graphical user interface, a camera, a lot
of memory or complex network software, a microcontroller is no longer enough.
Application processors run an operating system with virtual memory such as
Linux. The last part of this chapter summarises their features and gives a
checklist for choosing a processor.}

\begin{description}
\item[{\rot\bf Application processors}]~\\[-\lblskip]
\bi
	\ite ARM Cortex-A (and RISC-V application cores) with
	\bi
		\ite \textbf{MMU}: virtual memory, every process has its own protected address space -- required by Linux
		\ite several cores, GHz clock rates, multi-level caches, out-of-order execution in larger cores
		\ite external DRAM (hundreds of MB to several GB), storage on eMMC or SD card
	\ei
	\ite examples: Raspberry Pi 5 (4 $\times$ Cortex-A76, 2.4\,GHz), NXP i.MX\,8/9, TI AM62x, STM32MP1/MP2 (Cortex-A + Cortex-M on one chip)
	\ite often with GPU, video codecs and neural network accelerators (NPU)
	\ite non-deterministic timing (caches, DRAM, branch prediction) $\Rightarrow$ hard real time on a separate core or MCU
\ei
\os{\newpage}

\item[{\rot\bf Choosing a processor: checklist}]~\\[-\lblskip]
\bi
	\ite \textbf{function}: required peripherals (number of UARTs, ADC resolution, CAN, USB, Ethernet, radio)
	\ite \textbf{performance}: computing power, FPU or DSP needed? Real-time requirements?
	\ite \textbf{memory}: flash and RAM with reserve for later updates (rule of thumb: start with 50\,\% usage at most)
	\ite \textbf{energy}: battery or mains? Sleep current, wake-up time
	\ite \textbf{environment}: temperature range, automotive or industrial qualification, safety certification
	\ite \textbf{software}: compilers, SDK, RTOS and Rust support, example code, community
	\ite \textbf{business}: price at the planned quantity, availability for 10+ years, second source
	\ite in practice the software ecosystem and the availability decide more often than the core itself
\ei
\os{\newpage}

\item[{\rot\bf Exercises}]~\\[-\lblskip]
\bi
	\ite Compile \texttt{sum.c} on \url{https://godbolt.org} for the Cortex-M0+ with \texttt{-O0}, \texttt{-Os} and \texttt{-O2}. Compare the number of instructions in the loop.
	\ite Change the type of \texttt{s} to \texttt{uint16\_t}. Which processor profits most, and why?
	\ite Change \texttt{a} to \texttt{const float *} and \texttt{s} to \texttt{float}. Which instructions does the compiler generate for the Cortex-M0+, the Cortex-M4 (\texttt{-mfloat-abi=hard -mfpu=fpv4-sp-d16}) and the ESP32-C3?
	\ite Estimate the battery lifetime of a sensor that wakes up every minute for 50\,ms at 20\,mA and sleeps at 5\,$\mu$A (battery 1000\,mAh).
	\ite Choose a microcontroller for a battery-powered weather station that sends data via Wi-Fi every 15 minutes. Justify your choice with the checklist.
\ei
\end{description}

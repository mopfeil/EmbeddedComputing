\section{Programming in Assembler}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\nsl{The method of programming a microcontroller is little bit different from that used for programming of microprocessors. In the case of microcontrollers, the programming is usually done using the ``cross compilation'' technique. In this method, all the necessary tools for compiling are installed on a PC (i.e. editor, compiler, linker etc.) and the executable file generated is then downloaded to the target system. Here, the target system (e.g. ARM-Cortex-A8) has a completely different processing core than the host PC (which employs e.g. an Intel Processor).
\newline
Another method involves development on the target directly and doesn't have a download mechanism. The target processor and the processor for the development system is the same and a loader of an available operating system loads the executable file and starts the program.
\newline
A next important difference between the development of programs for microcontroller and microprocessor is the opportunity to use an operating system or not. In nearly every application which uses a microprocessor there is support from an operating system (OS). Simple input/output-operations, memory allocation and mathematical libraries would be offered through the operating system. In the case of a microcontroller you have to program all these functions.
\newline
The microcontroller ARM-Cortex-A8 is a processor just on the border between microprocessors and microcontrollers. From the point of a programmer it is a typical microprocessor, from the point of a hardware designer it is a highly sophisticated microcontroller. So in this chapter we don't find the specific restrictions which are typical for other microcontrollers. Starting with an overview about all the registers (register model) from the different parts of this controller we will progress to assembler programming aspects. The focus is to understand the specific aspects of this controller and not to write big assembler programs. These could be better done through C-programs.
}

\item[{\rot\bf Register model}]~\\[-3ex]
\bigskip
\bi
	\ite the register model of all ARM processors first introduce the ALU register set
	\ite the ALU registers are used for data operations and for address calculations
	\ite a few register are only visible in the different processor mode (like user mode, system mode, supervisor mode .. )
	\ite other processor units (like FPU, NEON) use there one register sets
	\ite register models are important for the development of assembler programs (a C-compiler tries to hide the most aspects of registers).
	\ite registers are part of the core (not mapped in the address space of the memory).
	\bigskip
	\ite register model for integer operations (core register).
	\bi
		\ite register r0 - r12 used for data- and address-operation
		\ite register r13 \pr stack (address register for the stack)
		\ite register r14 \pr link (address register for the return address of a subroutine)
		\ite register r15 \pr pc (address register for the next instruction)
		\ite the access to a data-register could be done as a Byte (b), Halfword (h) (16-bit) or Word (32-bit) (default).
		\ite the access to an address-register only a Word is possible.
	\ei
\ei

	\ite C \pr Carry flag (set if a carry out of the most significant bit of the operand occurs for an addition, or if a borrow occurs in a subtraction; otherwise cleared); for unsigned numbers.

\item[{\rot\bf Addressing modes}]~\\[-3ex]
\os{\bigskip}
\bi
	\ite addressing modes could be separated in five groups
	\bigskip
	\ite {\rot\bf Register addressing}
	\bi
		\ite name of the register coded in the instruction
		\\ \begin{tabular}{l l}
		      LDR r0,r1 &;load the contents form r1 to r0 (32 bit, default) \\
		      LDRB r2,r0 &;load the least significant byte from r0 to r2 \\
			& ;(least significant position)\\
		      LDRH r3,r2 &;load the least significant halfword from r2 to r3\\
			& ;(same position in r3)\\
			& \\
		      SDR r0,r1 &;store the contents form r0 to r1 (32 bit, default) \\
		      SDRB r2,r0 &;store the least significant byte from r2 to r0\\
			& ;(least significant position)\\
		      SDRH r3,r2 &;store the least significant halfword from r3 to r2 (same position in r2)\\
			& \\
		      MOV r0,r1 & ;transfer contents form r0 to r1 (allways 32 bit) \\
		      MOVS r0,r1 & ;transfer contents form r0 to r1 (allways 32 bit)\\
			& ;and set the Z- and N-flag
		     \end{tabular}
		\ite RISC-like register instructions
		\\ \begin{tabular}{l l}
		      LDR r15,r14 &;load PC with the contents of the link register\\
			& ;\pr same as RET-instruction\\
		      MSR r4,CPSR &;move the contents of CPSR to r4 (32 bit)\\
		      MRS CPSR\_f,r4 &;move the flag-field \\
			& ;(5 most significant bits \pr N-, Z-, C-, V-, Q-flag)\\
		   \end{tabular}

	\ei
	\os{\newpage}
	\ite {\rot\bf Immediate addressing}
	\bi
		\ite instruction contains the data
		\ite the immediate value is signed (-4095 to +4096 for LDR-instruction)
		\ite this type of addressing is useful for source addressing only
		\\ \begin{tabular}{l l}
		      LDR r0,\#0x100 & ;transfer the value 100 (hex)to r0 (32 bit)\\
		      LDR r0,\#0x-100 & ;transfer the value -100 (hex)to r0 (32 bit)\\
			& \\
		      LDR r0,=\#0x2000 & ;transfer the value 2000 (hex)\\
			& ;to r0 (pseudo-instruction)\\
			& ;LDR r0,=\#0x2000 \pr LDR r0,[pc,offset\_to\_litpool]\\
			& ;...\\
			& ;litpool DCD 0x2000
		     \end{tabular}

	\ei
	\os{\newpage}
	\ite {\rot\bf Direct addressing}
	\bi
		\ite instruction contains the address of a data
		\ite not directly implemented, an direct or absolut address could be given with a pseudo-instruction
		\\ \begin{tabular}{l l}
		      LDR r0,=label &;load the register r0 with address of label\\
			& ;LDR r0=label \pr LDR r0,[pc,offset\_to\_litpool]\\
			& ;...\\
			& ;litpool DCD label;\\
		     \end{tabular}

	\ei
	\os{\newpage}
	\ite {\rot\bf Indirect addressing}
	\bi
		\ite use one of the registers r0 - r12.
		\ite address registers r13 - a15 are special address registers.
		\ite address registers are always 32-bit registers.
		\ite indirect addressing modes operate in different versions.
		\bigskip
		\ite {\rot\bf Indirect addressing standard}
		\\ \begin{tabular}{l l}
		      LDR r1,[r0] & ;load the register r1 with contents\\
			& ;of address where r0 points to\\
		      SDR r2,[r0] & ;store the register r2 to the address\\
			& ;where r0 points to\\
		     \end{tabular}
		\os{\newpage}
		\ite {\rot\bf Indirect addressing with index and offset}
		\ite address calculation with an address register and an additional register and a offset
		\ite the additional register and the offset are signed.
		\\ \begin{tabular}{l l}
		      LDR r0,[r1,r2,0x20] &;load register r0 from the address given by\\
			& ;r1 + r2 + 0x20\\
		      SDR r0,[r1,-r2,-0x20] &;store register r0 at the address given by \\
			& ;r1 - r2 - 0x20\\
		     \end{tabular}
		\bigskip
		\ite {\rot\bf Indirect addressing with index,offset and update}
		\ite address calculation with an address register and an additional register and a offset
		\ite the additional register and the offset are signed.
		\ite after the transfer the first mentioned address register are updated
		\\ \begin{tabular}{l l}
		      LDR r0,[r1,r2,0x20]! &;load register r0 from the address given by \\
			& ;r1 + r2 + 0x20, r1 updated\\
		      SDR r0,[r1,-r2,-0x20]! &;store register r0 at the address given by \\
			& ;r1 - r2 - 0x20, r1 updated\\
		     \end{tabular}
		\os{\newpage}

		\ite{\rot\bf post increment / pre decrement}
		\ite load and store registers from stack
		\\\begin{tabular}{l l}
		      LDMFA r13!,\{r0 - r12\} & ;load stackframe (r13) to registers r0 - r12 \\
			& ;full asscending stack\\
			& ;increment register r13 and store\\
			& ;the last position of the stack in r13 \\
			& ;(pop-operation on Intel processors)\\
			& \\
		     STMFD r13!\{r0 - r12\}, & ;generate a stackframe r0 - r12 \\
			& ;full descending stack\\
			& ;save registers r0 - r12 on the stack\\
			& (push-operation on Intel processors)\\
			& \\
		     STMFD  r13!,\{r4 - r12,LR\} & ;push registers r4 - r12 to the stack\\
			& ;and place the return address (LR)\\
			& ;on the stack\\
		     LDMFA r13!,\{r4 - r12,PC\} & pop registers r 4 - r12 from the stack\\
			& ;and jump back to the calling routine\\
		     \end{tabular}
		\os{\newpage}
		\ite post inrement and predecrement addressing mode work which other register as the stack also
		\\\begin{tabular}{l l}
		      LDMIA / STMIA... & ;increment after transfer\\
		      LDMIB / STMIB... & ;increment before transfer\\
		      LDMDA / STMDA... & ;decrement after transfer\\
		      LDMDB / STMDB... & ;decrement before transfer\\
		
		 \end{tabular}
		\bigskip
		
	\ei
	\os{\newpage}
	\ite {\rot\bf Relative addressing}
	\bi

		\ite easier use of relative the relative addressing mode with the pseudo instruction ADR

	\ite Cross compilation:
	\ite use of a special toolchain to build programs for ARM-Cortex-A8

\item[{\rot\bf Running Python - The Interpreter}]~\\[-3ex]

\vspace{1cm}
\bi
\ite Python is an interpreted language and not a compiled one, although compilation is a step.
\ite Python code, written in a .py file is first compiled to what is called bytecode.
\ite Stored with a .pyc or .pyo format
\ite bytecode is a low-level set of instructions that can be executed by an interpreter.
\ite mostly at /usr/local/bin/pythonx.x.
\ite Instead of executing the instructions on CPU, bytecode instructions are executed on a Virtual Machine.
\ei

\os{\newpage}


\item[{\rot\bf Why to interpret?}]~\\[-3ex]

\vspace{1cm}
\bi
\ite Platform-independent
\bi
\ite As long as the Python bytecode and the Virtual Machine have the same version, Python bytecode can be executed on any platform (Windows, MacOS, etc).
\ei
\ite Dynamic typing
\bi
\ite In static-typed languages like C++, you have to declare the variable type and any discrepancy like adding a string and an integer is checked during compile time.
\ite In strongly typed languages like Python, it is the job of the interpreter to check the validity of the variable types and operations performed.
\ei

\item[{\rot\bf 	BOUNDARY SCAN PRINCIPLE}]~\\[-3ex]

\vspace{1cm}
\bi
\ite How does it work?
\ite 	The top level schematic of the test logic defined by IEEE Std 1149.1 includes three key blocks:
\ite      The TAP Controller
\ite 	This responds to the control sequences supplied through the test access port (TAP) and generates the clock and control signals required for correct operation of the other circuit blocks.
\ite       The Instruction Register
\ite      	This shift register-based circuit is serially loaded with the instruction that selects an operation to be performed.
\ite      The Data Registers
\ite      	These are a bank of shift register based circuits. The stimuli required by an operation are serially loaded into the data registers selected by the current instruction. Following execution of the operation, results can be shifted out for examination.
\ei

\os{\newpage}


\item[{\rot\bf 	JTAG Test Access Port}]~\\[-3ex]

\vspace{1cm}
\bi
\ite The JTAG Test Access Port (TAP) contains four pins that drive the circuit blocks and control the operations specified. The TAP facilitates the serial loading and unloading of instructions and data.
\ite 	The four pins of the TAP are:
\ite 	TMS - Test Mode Select
\ite 	TCK - Test Clock
\ite 	TDI - Test Data Input
\ite    TDO - Test Data Output
\ei

\os{\newpage}


\item[{\rot\bf 	JTAG Test Access Port (Contd)}]~\\[-3ex]

\vspace{1cm}
\bi
\ite The function of each TAP pin is as follows:
\ite TCK - this pin is the JTAG test clock. It sequences the TAP controller as well as all of the JTAG registers
\ite TMS - this pin is the mode input signal to the TAP Controller. The state of TMS at the rising edge of TCK determines the sequence of states for the TAP controller.
\ei

\os{\newpage}


\item[{\rot\bf 	JTAG Test Access Port (Contd)}]~\\[-3ex]

\vspace{1cm}
\bi
\ite TDI - this pin is the serial data input to all JTAG instruction and data registers. TDI is sampled into the JTAG registers on the rising edge of TCK.
\ite TDO - this pin is the serial data output for all JTAG instruction and data registers. TDO changes state on the falling edge of TCK and is only active during the shifting of data through the device. This pin is three-stated at all other times
\ei

\os{\newpage}


\item[{\rot\bf 	JTAG TAP Controller}]~\\[-3ex]

\vspace{1cm}
\bi
\ite 	The JTAG TAP Controller is a
\ite 16-state finite state machine, that controls the scanning of data into the various registers of the JTAG architecture.
\ite The state of the TMS pin at the rising edge of TCK is responsible for determining the sequence of state transitions.
\ite There are two state transition paths for scanning the signal at TDI in to the device,
\bi
\ite one for shifting in an instruction to the instruction register ,and ,
\ite  one for shifting data into the active data register as determined by the current instruction.
\ei
\ei

\item[{\rot\bf        Data Registers}]~\\[-3ex]

\vspace{1cm}
\bi
\ite The Device ID register (IDR) reads-out an identification number which is hardwired into the chip.
\ite The Bypass register (BR) is a 1-cell pass-through register which connects the TDI to the TDO with a 1-clock delay to give test equipment easy access to another device in the test chain on the same board.
\ite The Boundary Scan register (BSR), intercepts all the signals between the core-logic and the pins.
\ei

\os{\newpage}


\item[{\rot\bf 			Test Process}]~\\[-3ex]

\vspace{1cm}
\bi
\ite     The standard test process for verifying a device or circuit board using boundary-scan technology is as follows:
\ite The tester applies test or diagnostic data on the input pins of the device.
\ite The boundary-scan cells capture the data in the boundary scan registers monitoring the input pins.
\ite Data is scanned out of the device via the TDO pin, for verification.
\ite Data can then be scanned into the device via the TDI pin.
\ite The tester can then verify data on the output pins of the device.
\ei

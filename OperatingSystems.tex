\section{Why an Operating System?}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\nsl{Small embedded programs often consist of one endless loop that polls
inputs and calls functions in turn, plus some interrupt service routines.
This works well as long as all jobs are short and have similar timing
requirements. It becomes hard when one job takes long (a network transfer,
a display update) while another must react within milliseconds. A real-time
operating system (RTOS) solves this by splitting the program into tasks.
Each task is written as if it had the processor to itself, and a scheduler
decides which task runs. The scheduler always picks the most important ready
task, so the reaction time of high priority tasks no longer depends on the
others.
\newline
In this chapter we look at the concepts behind an RTOS and at two ways to
apply them on the ESP32-C3: FreeRTOS in C, which the Arduino core and
ESP-IDF are built on, and the async framework Embassy in Rust. At the end we
compare other systems, up to embedded Linux on larger processors.
\newpage}

\begin{description}
\item[{\rot\bf Program structures without an operating system}]~\\[-3ex]
\bi
	\ite \textbf{super loop}: \texttt{for(;;) \{ read(); control(); show(); \}}
	\bi
		\ite simple, deterministic, no extra memory
		\ite the reaction time is the duration of the whole loop -- one slow function delays everything
		\ite waiting (``\texttt{delay(500)}'') blocks all other jobs
	\ei
	\ite \textbf{foreground / background}: interrupts for urgent events (foreground), super loop for the rest (background)
	\bi
		\ite fast reaction to events
		\ite the ISRs must stay short; shared variables need protection; long work still ends up in the loop
	\ei
	\ite both are fine for small systems -- many products never need more
\ei
\os{\newpage}

\item[{\rot\bf What an RTOS adds}]~\\[-3ex]
\bi
	\ite \textbf{tasks} (threads): independent functions, each with its own stack and priority
	\ite \textbf{scheduler}: decides which ready task runs; preempts a task when a more important one becomes ready
	\ite \textbf{time services}: delays, periodic execution, timeouts
	\ite \textbf{communication and synchronisation}: queues, semaphores, mutexes, event flags
	\ite \textbf{memory management}: task stacks, heap for dynamic objects
	\ite costs: a few KB of code (FreeRTOS kernel about 6--12\,KB), RAM for every task stack, some microseconds per task switch, and new kinds of errors (race conditions, deadlocks)
\ei
\os{\newpage}

\item[{\rot\bf Real time}]~\\[-3ex]
\bi
	\ite real time means \textbf{predictable}, not ``fast'': the result must be there before its \textbf{deadline}
	\bi
		\ite \textbf{hard} real time: a missed deadline is a failure (airbag, motor control)
		\ite \textbf{soft} real time: a missed deadline reduces the quality (audio dropout, slow display)
	\ei
	\ite important figures
	\bi
		\ite \textbf{latency}: time from an event to the start of the reaction
		\ite \textbf{jitter}: variation of this time or of a period
		\ite \textbf{WCET} (worst case execution time): the longest time a piece of code can take -- the average is not enough
	\ei
	\ite an RTOS makes timing analysable: the highest priority ready task always runs, kernel operations have bounded duration
	\ite general purpose systems (Windows, standard Linux) optimise throughput and fairness instead
\ei
\os{\newpage}
\end{description}

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\section{Tasks and Scheduling}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\nsl{A task is a function that usually never returns. The kernel keeps a
task control block (TCB) for every task, with its state, its priority and
the saved stack pointer. When the scheduler switches from one task to
another, it saves the registers of the running task on its stack and
restores those of the next task. Each task therefore has its own stack,
which is the main memory cost of an RTOS. A task that waits for something,
such as a time, a message or a lock, is blocked and uses no processor time
at all.}

	\ite on a single core exactly one task is Running; the idle task (lowest priority) runs when nothing else is ready

\item[{\rot\bf Preemptive priority scheduling}]~\\[-3ex]
\bi
	\ite every task has a fixed priority (FreeRTOS: higher number = more important)
	\ite the scheduler always runs the ready task with the highest priority
	\ite when a more important task becomes ready (timeout, message, interrupt), the running task is interrupted at once -- \textbf{preemption}
	\ite tasks with the same priority share the CPU in turns (time slicing at every tick)
	\ite the \textbf{tick} interrupt (1\,ms on the ESP32) drives delays and time slicing
	\ite the context switch itself is done in a special low-priority interrupt (on Cortex-M: PendSV), so it never interrupts another ISR
\ei

\item[{\rot\bf Choosing priorities}]~\\[-3ex]
\bi
	\ite priority follows urgency (deadline), not ``importance'' of the function
	\ite \textbf{rate monotonic} assignment for periodic tasks: shorter period $\Rightarrow$ higher priority
	\bi
		\ite with $n$ independent periodic tasks all deadlines are met if the CPU utilisation $U = \sum C_i/T_i \le n(2^{1/n}-1)$ (about 69\,\% for large $n$; $C_i$ = execution time, $T_i$ = period)
	\ei
	\ite long computations get a low priority; reactions to events a high one
	\ite a task that never blocks starves all tasks with lower priority -- every task must wait somewhere
	\ite ISRs are always more urgent than any task: keep them short and hand the work to a task
\ei
\os{\newpage}

\item[{\rot\bf FreeRTOS: creating tasks}]~\\[-3ex]
\begin{lstlisting}[language=C]
void blinkTask(void *param) {
  pinMode(LED, OUTPUT);
  for (;;) {
    digitalWrite(LED, !digitalRead(LED));
    vTaskDelay(pdMS_TO_TICKS(500));          // blocked for 500 ms
  }
}
void heartbeatTask(void *param) {
  TickType_t lastWake = xTaskGetTickCount();
  for (uint32_t n = 0;; n++) {
    Serial.printf("heartbeat %lu at %lu ms\n", (unsigned long)n, (unsigned long)millis());
    xTaskDelayUntil(&lastWake, pdMS_TO_TICKS(1000));   // fixed period, no drift
  }
}
void setup() {
  Serial.begin(115200);
  // function, name, stack size (ESP-IDF: in BYTES), parameter, priority, handle
  xTaskCreate(blinkTask, "blink", 2048, NULL, 2, NULL);
  xTaskCreate(heartbeatTask, "heartbeat", 4096, NULL, 1, NULL);
}
\end{lstlisting}
\bi
	\ite \texttt{vTaskDelay}: relative, the period drifts; \texttt{xTaskDelayUntil}: absolute (Wokwi: 1178, 2178, 3178\,ms)
\ei
\os{\newpage}

\item[{\rot\bf Embassy: tasks as async functions (Rust)}]~\\[-3ex]
\begin{lstlisting}[language=Rust]
/// A task is an async function. It runs until it awaits something and
/// then gives the CPU to the next ready task.
#[embassy_executor::task]
async fn blink(mut led: Output<'static>) {
    let mut ticker = Ticker::every(Duration::from_millis(500));
    loop {
        led.toggle();
        ticker.next().await; // fixed period, does not drift
    }
}

#[esp_rtos::main]
async fn main(spawner: Spawner) -> ! {
    // ... init ...
    let led = Output::new(peripherals.GPIO4, Level::Low, OutputConfig::default());
    spawner.spawn(blink(led).unwrap());
    spawner.spawn(heartbeat().unwrap());
    loop {
        embassy_time::Timer::after_secs(3600).await;
    }
}
\end{lstlisting}
\bi
	\ite the LED is \textbf{moved} into the task: no other part of the program can use it any more
\ei
\os{\newpage}

\item[{\rot\bf How Embassy differs from FreeRTOS}]~\\[-3ex]
\bi
	\ite the compiler turns every \texttt{async fn} into a state machine; \texttt{.await} = ``save the state, return to the executor''
	\ite \textbf{no stack per task}: the state machine contains only the variables that live across an \texttt{.await}, and its size is known at compile time $\Rightarrow$ all memory is static, no stack overflows of tasks
	\ite \textbf{cooperative} within one executor: a task runs until its next \texttt{.await} -- a long computation without \texttt{.await} blocks all other tasks
	\ite priorities: several executors, e.g.\ an \texttt{InterruptExecutor} that runs inside an interrupt with higher priority
	\ite when no task is ready, the executor puts the CPU to sleep (\texttt{wfi}) -- good for battery devices
	\ite hardware events wake tasks directly: the interrupt handler calls the task's \textbf{waker}
\ei
\os{\newpage}
\end{description}

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\section{Communication and Synchronisation}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\nsl{Tasks rarely work alone. They pass data to each other, wait for
events from interrupts and share resources such as a bus, a display or a
global variable. The kernel offers objects for this: queues to pass data,
semaphores to signal events, and mutexes to protect shared resources. Used
carelessly they lead to the classic errors of concurrent programs: race
conditions, deadlocks and priority inversion. All three can be shown in
a few lines of code, and our examples do exactly that.}

\begin{description}
\item[{\rot\bf Queues: passing data between tasks}]~\\[-3ex]
\bi
	\ite a FIFO buffer with a fixed number of elements; the data is \textbf{copied} into the queue
	\ite sending to a full queue and receiving from an empty queue \textbf{block} the task (with an optional timeout)
	\ite the receiver needs no polling: it sleeps until data arrives
	\ite decouples producer and consumer: different speeds, different priorities
\ei
\begin{lstlisting}[language=C]
QueueHandle_t samples = xQueueCreate(8, sizeof(uint16_t));   // 8 elements

void producerTask(void *param) {                 // every 100 ms
  for (;;) {
    uint16_t raw = analogRead(POT);
    xQueueSend(samples, &raw, portMAX_DELAY);   // waits if the queue is full
    xTaskDelayUntil(&lastWake, pdMS_TO_TICKS(100));
  }
}
void consumerTask(void *param) {                 // average of 10 values
  for (;;) {
    uint32_t sum = 0;
    for (int i = 0; i < 10; i++) {
      uint16_t value;
      xQueueReceive(samples, &value, portMAX_DELAY);   // waits for data
      sum += value;
    }
    Serial.printf("average of 10 samples: %lu\n", (unsigned long)(sum / 10));
  }
}
\end{lstlisting}
\os{\newpage}

\item[{\rot\bf Queues in Embassy: channels}]~\\[-3ex]
\begin{lstlisting}[language=Rust]
/// Queue for 8 values. A full queue makes send() wait (back pressure),
/// an empty queue makes receive() wait.
static SAMPLES: Channel<CriticalSectionRawMutex, u16, 8> = Channel::new();

#[embassy_executor::task]
async fn consumer() {
    loop {
        let mut sum: u32 = 0;
        for _ in 0..10 {
            sum += SAMPLES.receive().await as u32; // waits for the next value
        }
        println!("average of 10 samples: {}", sum / 10);
    }
}

// in main (producer):
let mut ticker = Ticker::every(Duration::from_millis(100));
loop {
    let raw: u16 = nb::block!(adc.read_oneshot(&mut pot)).unwrap();
    SAMPLES.send(raw).await; // producer
    ticker.next().await;
}
\end{lstlisting}
\os{\newpage}

\item[{\rot\bf From interrupt to task}]~\\[-3ex]
\bi
	\ite \textbf{deferred interrupt handling}: the ISR only acknowledges the hardware and signals a task; the task does the real work
	\bi
		\ite the ISR stays short $\Rightarrow$ small latency for all other interrupts
		\ite the work runs with a task priority and may block, print, use the network
	\ei
	\ite \textbf{semaphore}: a counter; \texttt{give} increments, \texttt{take} decrements or blocks at 0
	\bi
		\ite binary semaphore (0/1) to signal an event; counting semaphore to count events or free resources
	\ei
	\ite in an ISR only the \texttt{...FromISR} functions are allowed: they never block, and they report whether a more important task was woken up
	\ite FreeRTOS also offers direct \textbf{task notifications}: faster and smaller than a semaphore when exactly one task waits
\ei
\os{\newpage}

\item[{\rot\bf Interrupt to task: C and Rust}]~\\[-3ex]
\begin{lstlisting}[language=C]
void IRAM_ATTR onButton() {          // ISR: as short as possible
  BaseType_t woken = pdFALSE;
  xSemaphoreGiveFromISR(buttonSem, &woken);   // never the normal API in an ISR
  portYIELD_FROM_ISR(woken);         // switch at once if a higher task woke up
}
void buttonTask(void *param) {
  for (;;) {
    xSemaphoreTake(buttonSem, portMAX_DELAY);   // sleep until the ISR gives
    // ... toggle LED, print, debounce ...
  }
}
\end{lstlisting}
\begin{lstlisting}[language=Rust]
loop {
    button.wait_for_falling_edge().await; // interrupt wakes the task
    presses += 1;
    led.toggle();
    Timer::after_millis(50).await; // debounce: ignore the bouncing
    button.wait_for_high().await; // wait until released
}
\end{lstlisting}
\bi
	\ite in Rust the interrupt, the flag and the waiting are hidden behind one \texttt{.await}; tested in Wokwi with bouncing buttons: two presses $\rightarrow$ exactly two events
\ei
\os{\newpage}

\item[{\rot\bf Race conditions}]~\\[-3ex]
\bi
	\ite two tasks change the same variable with read -- modify -- write
	\ite a task switch between read and write $\Rightarrow$ the other task's update is overwritten (``lost update'')
	\ite the error appears rarely and randomly -- very hard to find by testing
\ei
\begin{lstlisting}[language=C]
for (int i = 0; i < 1000; i++) {     // in two tasks of equal priority
  if (useMutex) xSemaphoreTake(lock, portMAX_DELAY);
  uint32_t value = counter;          // read
  taskYIELD();                       // provoke a task switch right here
  counter = value + 1;               // modify-write
  if (useMutex) xSemaphoreGive(lock);
}
\end{lstlisting}
\begin{lstlisting}[language={}]
without mutex: counter = 1001 (expected 2000)
with    mutex: counter = 2000 (expected 2000)
\end{lstlisting}
\bi
	\ite the \texttt{taskYIELD()} makes the error certain; in real code an interrupt or the tick causes it from time to time
\ei
\os{\newpage}

\item[{\rot\bf Mutual exclusion}]~\\[-3ex]
\bi
	\ite the code between read and write is a \textbf{critical section}: only one task at a time may execute it
	\ite ways to protect it
	\bi
		\ite disable interrupts / the scheduler: very short sections only (a few instructions), affects the whole system
		\ite \textbf{mutex} (mutual exclusion): a lock that only the task that took it may release; other tasks block while it is taken
	\ei
	\ite in Rust, data shared between tasks must be wrapped in a type that guarantees exclusive access; writing to a plain global variable requires \texttt{unsafe}
\ei
\begin{lstlisting}[language=Rust]
static COUNTER: Mutex<CriticalSectionRawMutex, u32> = Mutex::new(0);

for _ in 0..1000 {
    let mut counter = COUNTER.lock().await; // wait until the mutex is free
    let value = *counter; // read
    Timer::after(Duration::from_micros(10)).await; // other task may run now
    *counter = value + 1; // modify-write
} // guard dropped here -> mutex released
\end{lstlisting}
\bi
	\ite the data is only reachable through the lock, and the lock is released automatically -- forgetting it is impossible
\ei
\os{\newpage}

\item[{\rot\bf Deadlock}]~\\[-3ex]
\bi
	\ite two tasks wait for each other forever: A holds lock 1 and waits for lock 2, B holds lock 2 and waits for lock 1
	\ite possible only if all four conditions hold: mutual exclusion, hold and wait, no preemption of locks, circular wait
	\ite prevention in practice
	\bi
		\ite always take several locks in the same, fixed order
		\ite hold locks as short as possible; never block (queue, delay) while holding a lock
		\ite use timeouts instead of waiting forever, and report the timeout
		\ite better: avoid sharing -- let one task own the resource and send it requests through a queue
	\ei
\ei
\os{\newpage}

\item[{\rot\bf Priority inversion}]~\\[-3ex]
\bi
	\ite a low priority task L holds a lock that the high priority task H needs $\Rightarrow$ H must wait for L (unavoidable, but short)
	\ite a medium priority task M, which does not need the lock, preempts L $\Rightarrow$ H effectively waits for M: the priorities are inverted
	\ite famous case: Mars Pathfinder (1997) -- repeated resets by the watchdog until priority inheritance was switched on remotely
	\ite solution: \textbf{priority inheritance} -- while L holds a mutex that H waits for, L runs with H's priority, so M cannot preempt it
	\bi
		\ite FreeRTOS mutexes do this; binary semaphores do not
	\ei
\ei

\item[{\rot\bf Memory in an RTOS}]~\\[-3ex]
\bi
	\ite every task needs its own stack -- too small is the most common RTOS error
	\bi
		\ite the stack overflows silently into other data; use the overflow check of the kernel (\texttt{configCHECK\_FOR\_STACK\_OVERFLOW}) and measure the high water mark (\texttt{uxTaskGetStackHighWaterMark})
		\ite \texttt{printf} and floating point need much stack -- on the ESP32 4\,KB are a safe start for such tasks
	\ei
	\ite kernel objects (tasks, queues, semaphores) can be allocated
	\bi
		\ite dynamically from the RTOS heap: simple, but the heap can fragment and allocation can fail at run time
		\ite statically (\texttt{xTaskCreateStatic}, \ldots): all memory is known at link time -- preferred in safety-related systems
	\ei
	\ite FreeRTOS offers several heap implementations: from ``allocate only, never free'' (heap\_1) to a general allocator that merges free blocks (heap\_4)
	\ite Embassy: everything static; the size of every task's state is checked by the compiler
\ei
\os{\newpage}
\end{description}

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\section{Operating Systems for Embedded Systems}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\nsl{FreeRTOS is only one of many options. The choice depends on the
hardware (microcontroller or application processor with a memory management
unit), on the required functions (network stack, file system, drivers), on
certification needs, on the language and on the license. This section
gives an overview. At the upper end, embedded Linux is used whenever the
hardware is large enough and complex functions such as graphical user
interfaces, many network protocols or containers are needed.}

\begin{description}
\item[{\rot\bf Real-time systems for microcontrollers}]~\\[-3ex]
\begin{center}
\resizebox{0.95\textwidth}{!}{%
\begin{tabular}{|l|l|l|}
\hline
\textbf{system} & \textbf{characteristics} & \textbf{license} \\
\hline
FreeRTOS & small kernel, very widely used, basis of ESP-IDF & MIT \\
Zephyr & complete OS with drivers, networking, Bluetooth; device tree & Apache 2.0 \\
Embassy & async Rust: executor, HALs, networking, USB, Bluetooth & MIT / Apache 2.0 \\
RTIC & Rust: tasks = interrupt handlers, deadlock-free by design & MIT / Apache 2.0 \\
Eclipse ThreadX & formerly Azure RTOS; certified for safety standards & MIT \\
NuttX & POSIX interface, ``small Linux'' for microcontrollers & Apache 2.0 \\
commercial & VxWorks, QNX, embOS, SafeRTOS: certified, with support & commercial \\
\hline
\end{tabular}}
\end{center}
\bi
	\ite safety standards (IEC 61508, ISO 26262 for cars) require a certified kernel or a large verification effort
\ei
\os{\newpage}

\item[{\rot\bf Embedded Linux}]~\\[-3ex]
\bi
	\ite needs an application processor with \textbf{MMU} and typically $\ge$ 64\,MB RAM (Raspberry Pi, i.MX, STM32MP, AM62x)
	\ite advantages: complete network stack, file systems, USB, graphics, thousands of existing programs, high level languages, containers
	\ite disadvantages: boot time of seconds, much more memory and energy, larger attack surface, regular security updates necessary
	\ite real time: the standard kernel gives no guarantees; \textbf{PREEMPT\_RT} (part of the mainline kernel since 6.12, 2024) reduces latencies to some 10\,$\mu$s
	\ite common architecture: Linux for user interface and communication, plus a microcontroller (often on the same chip) running an RTOS for the hard real-time part
\ei
\os{\newpage}

\item[{\rot\bf Booting embedded Linux}]~\\[-3ex]

\item[{\rot\bf Building embedded Linux: cross development}]~\\[-3ex]
\bi
	\ite the target is too small (or too slow) to compile its own software $\Rightarrow$ \textbf{cross compiler} on the PC
	\bi
		\ite named by the target triple: \texttt{aarch64-linux-gnu-gcc}, \texttt{arm-linux-gnueabihf-gcc}
		\ite Rust: \texttt{rustup target add aarch64-unknown-linux-gnu} -- the same way we built for the RP2040 and the ESP32-C3
	\ei
	\ite build systems create the complete image (toolchain, bootloader, kernel, root file system) from source
	\bi
		\ite \textbf{Buildroot}: simple, configuration with \texttt{make menuconfig}, small images, quick to learn
		\ite \textbf{Yocto Project}: layers and recipes, reproducible, industry standard for products with long maintenance
	\ei
	\ite alternative for prototypes: a ready-made distribution (Raspberry Pi OS, Debian) and native compilation
	\ite the output format is the same as on microcontrollers: \textbf{ELF} files with sections for code (\texttt{.text}), data (\texttt{.data}, \texttt{.bss}) and debug information
\ei

\item[{\rot\bf Choosing the right approach}]~\\[-3ex]
\begin{center}
\resizebox{0.95\textwidth}{!}{%
\begin{tabular}{|l|l|l|}
\hline
\textbf{approach} & \textbf{suitable for} & \textbf{limits} \\
\hline
super loop + interrupts & small devices, simple timing & long jobs block everything \\
RTOS (FreeRTOS, Zephyr) & several jobs, different deadlines & stack per task, concurrency errors \\
async (Embassy) & event-driven, battery powered & long computations block \\
RTIC & hard real time, provable & interrupt-driven structure \\
embedded Linux & GUI, many protocols, complex software & boot time, memory, real time only with PREEMPT\_RT \\
\hline
\end{tabular}}
\end{center}

\item[{\rot\bf Exercises}]~\\[-3ex]

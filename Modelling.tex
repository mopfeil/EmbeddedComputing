\section{General Requirements}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\nsl{A small embedded project can start directly with programming: one
microcontroller, a few hundred lines of code, a test on the bench. Most
products are larger. Several developers, hardware and software designed in
parallel, safety requirements and a lifetime of many years make a more
structured approach necessary. Models describe the system before it is
built. They make it possible to discuss and check the behaviour, to
simulate it, to generate code and documentation from it, and to test the
implementation against it.
\newline
No single kind of model covers all aspects of an embedded system. This
chapter introduces the most important ones: state based models, which
describe how a system reacts to events, and activity oriented models, which
describe data flow and the order of operations. At the end we implement a
state machine in C and in Rust and run it on the Pico in Wokwi.
\newpage}

\bi
	\ite Classification of systems from the point of view of programming
\ei

\begin{figure}[!hbtp]
     \begin{center}
	  \epsfig{file=figures/Fig_2_1_Classification,width=0.7\textwidth}\\
	  \caption{Classification of embedded systems and real-time systems}
     \end{center}
\end{figure}
\os{\newpage}

\defn{def:embedded system}
{An \textbf{embedded system} is a computer system designed to perform a dedicated function within a larger mechanical or electronic system. Unlike a general-purpose computer, it performs one or a few pre-defined tasks, usually with specific requirements on timing, energy and reliability.}

\defn{def:reaktive systems}
{``A \textbf{reactive system} is one which is in continual interaction
  with its environment and executes at a pace determined by
  that environment'' [Berg\'{e}, 1995]}

\bi
	\ite interaction with the environment through sensors and actuators
	\ite minimum and maximum response times are part of the specification
	\ite the system may consist of parallel and distributed parts (subsystems)
\ei

\defn{def:real-time systems}
{A \textbf{real-time system} must deliver a correct result within a given time (its deadline). The correctness depends not only on the result but also on the time at which it is available.}

\bi
	\ite \textbf{hard} real time: missing a deadline is a failure of the system
	\ite \textbf{soft} real time: missing a deadline reduces the quality of the service
	\ite a real-time operating system helps to build a real-time system, but it is neither necessary nor sufficient (see chapter Operating Systems)
\ei

\os{\newpage}
\begin{description}
\item[{\rot\bf Requirements for models}]~\\[-\lblskip]
\bi
	\ite concurrency \pr real-time systems are usually concurrent
	\ite synchronisation and communication \pr modelling the communication between distributed parts
	\ite timing \pr deadlines, periods, response times
	\ite programming elements \pr arithmetic operations, loops and function calls should be expressible
	\ite non-standard I/O devices \pr switches, analog and digital I/O
	\ite non-functional properties \pr e.g.\ fault tolerance, availability, EMC, usability, extendibility, lifetime, power consumption
	\ite co-design \pr modelling of hardware and software functions
\ei
\item[{\rot\bf but}]~\\[-\lblskip]
\bi
	\ite models must be readable
	\ite models should be hierarchical \pr humans can only keep about 5 to 7 objects in mind at the same time
\ei
\qbox{A model should be as simple as possible, but not simpler. [attributed to A.\ Einstein]}
\end{description}

\begin{description}
\item[{\rot\bf Design methods}]~\\[-\lblskip]
\bi
	\ite capture and simulate
	\bi
		\ite specify the system, draw block diagrams (details not yet specified)
		\ite simulate and verify
	\ei
	\ite describe and synthesise
	\bi
		\ite generate hardware and software from the description with tools
		\ite logic synthesis from hardware description languages (VHDL, Verilog)
		\ite code generation from models (e.g.\ Simulink, state machine tools)
	\ei
	\ite specify -- explore -- refine
	\bi
		\ite tools support the exploration of alternatives (e.g.\ which functions in hardware, which in software)
		\ite the chosen solution is refined step by step
	\ei
\ei
\end{description}
\os{\newpage}

\begin{description}
\item[{\rot\bf Different views of a model}]~\\[-\lblskip]
\bi
	\ite behavioural view
	\bi
		\ite treats the system or parts of it as black boxes
		\ite focuses on states, processes, procedures
	\ei
	\ite structural view
	\bi
		\ite shows how the system is built from components and how they are connected
		\ite processors, boards, modules, buses
	\ei
	\ite physical view
	\bi
		\ite physical properties of the components: size, placement, heat, connections
	\ei
\ei
\item[{\rot\bf Classes of models}]~\\[-\lblskip]
\bi
	\ite no single model covers all requirements of an embedded system
	\ite each class of models focuses on certain aspects
	\bi
		\ite state oriented (state machines, StateCharts)
		\ite activity oriented (data flow graphs, flow charts, sequence diagrams)
		\ite structure oriented (block diagrams, component diagrams)
		\ite data oriented (entity relationship models)
		\ite heterogeneous (combinations, e.g.\ UML / SysML)
	\ei
\ei
\end{description}

\section{State Oriented Models}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\nsl{Most embedded systems react to events: a button is pressed, a value
exceeds a limit, a message arrives. What they do depends on the history,
which a state machine summarises in its current state. State machines are
easy to draw, easy to check (has every state a reaction to every input?)
and easy to implement. For large systems they become unwieldy, and
hierarchical state machines (StateCharts) were invented for this case.}

\bi
	\ite classical automata (FSM, \underline{f}inite \underline{s}tate \underline{m}achine) are state oriented models
	\ite two variants: Moore and Mealy machines
\ei

\begin{figure}[!hbtp]
     \begin{center}
	  \epsfig{file=figures/Fig_2_5_FSM,width=0.9\textwidth}\\
	  \caption{Block diagram of an FSM}
     \end{center}
\end{figure}

\os{\newpage}

\begin{eqnarray*}
&\textrm{Moore machine:} & Y = \lambda (Z), \quad Z^{+} = \delta(X,Z)\\
&\textrm{Mealy machine:} & Y = \lambda(X,Z), \quad Z^{+} = \delta(X,Z)\\[2ex]
&\lambda: & \textrm{output function}\\
&\delta: & \textrm{transition function, computes the next state } Z^{+}
\end{eqnarray*}
\bi
	\ite Moore: the output depends only on the state -- stable outputs, but one clock later
	\ite Mealy: the output depends on state and input -- faster reaction, fewer states
\ei
\os{\newpage}

\begin{figure}[!hbtp]
     \begin{center}
	  \epsfig{file=figures/Fig_2_6_FSM_Detail,width=0.8\textwidth}\\
	  \caption{FSM in more detail}
     \end{center}
\end{figure}

\os{\newpage}
\bi
	\ite flat FSMs are not useful for complex systems: too many states and transitions
	\ite hierarchy in state machines \pr StateCharts [Harel, 1987]
\ei

\begin{figure}[!hbtp]
     \begin{center}
	  \epsfig{file=figures/Fig_2_7_State_Chart,width=0.7\textwidth}\\
	  \caption{StateChart}
     \end{center}
\end{figure}
\os{\newpage}

\defn{def:State Chart}
{The current states of FSMs are called \textbf{active states}.\\
States which are not composed of other states are called \textbf{basic
states}.\\
States containing other states are called \textbf{super-states}.\\
A super-state S is called an \textbf{OR-super-state} if exactly one of its
sub-states is active whenever S is active.}

\begin{figure}[!hbtp]
     \begin{center}
	  \epsfig{file=figures/Fig_2_8_Activ_Substate,width=0.6\textwidth}\\
	  \caption{Active sub-state in a super-state}
     \end{center}
\end{figure}

\os{\newpage}
\bi
	\ite in an OR-super-state exactly one sub-state is active
	\ite concurrency cannot be modelled this way
\ei

\defn{def:AND-super-state}{A super-state S is called an \textbf{AND-super-state} if all of its sub-states are active whenever S is active.}

\begin{figure}[!hbtp]
     \begin{center}
	  \epsfig{file=figures/Fig_2_9_OR_AND_Super_States,width=0.8\textwidth}\\
	  \caption{Concurrency in an AND-super-state}
     \end{center}
\end{figure}
\os{\newpage}

\bi
	\ite AND-super-states \pr concurrent state machines
	\ite an AND-super-state is equivalent to the ``product'' of its sub-machines
\ei

\begin{figure}[!hbtp]
     \begin{center}
	  \epsfig{file=figures/Fig_2_10_AND_Superstate,width=0.8\textwidth}\\
	  \caption{Example of an AND-super-state}
     \end{center}
\end{figure}

\os{\newpage}

\begin{figure}[!hbtp]
     \begin{center}
	  \epsfig{file=figures/Fig_2_10_AND_Product,width=0.9\textwidth}\\
	  \caption{Decomposition of an AND-super-state into a product machine}
     \end{center}
\end{figure}
\os{\newpage}

\bi
	\ite \textbf{advantages of StateCharts}
	\bi
		\ite hierarchy allows arbitrary nesting of AND- and OR-super-states
		\ite well-defined semantics; many tools can simulate them
		\ite code generators produce C, C++ or VHDL
		\ite today part of UML and SysML (state machine diagrams)
	\ei
	\ite \textbf{disadvantages}
	\bi
		\ite generated code is sometimes inefficient
		\ite not suited for distributed systems
		\ite no description of non-functional behaviour or of the structure
	\ei
\ei
\os{\newpage}

\section{Implementing a State Machine}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\nsl{A state machine translates directly into code: one variable holds the
current state, and a function that is called periodically or for every event
computes the next state and the outputs. As an example we use a coffee
machine with two selection buttons and a ``ready'' signal. The same machine
is implemented in C with a \texttt{switch} statement and in Rust with
\texttt{enum} and \texttt{match}. Both versions run on the Pico in Wokwi.}

\begin{description}
\item[{\rot\bf Example: a coffee machine}]~\\[-\lblskip]
\bi
	\ite inputs: buttons \textbf{left} and \textbf{right}, signal \textbf{ready} (coffee finished)
	\ite outputs: add coffee, milk, sugar -- depend only on the state $\Rightarrow$ Moore machine
	\ite from idle: left = coffee with milk, right = coffee; then left = make it, right = add sugar
\ei
\begin{figure}[!hbtp]
     \begin{center}
	  \epsfig{file=figures/Fig_2_10_CoffeeMachine_FSM,width=0.28\textwidth}\\
	  \caption{Coffee machine FSM}
     \end{center}
\end{figure}
\os{\newpage}

\item[{\rot\bf State transition table}]~\\[-\lblskip]
\begin{center}
\resizebox{0.85\textwidth}{!}{%
\begin{tabular}{|l|l|l|l|c|}
\hline
\textbf{no.} & \textbf{state} & \textbf{left} & \textbf{right} & \textbf{output} \\
\hline
0 & idle (initial) & 2: coffee+milk & 1: coffee & 000 \\
1 & coffee & 5: make coffee & 3: coffee+sugar & 000 \\
2 & coffee+milk & 6: make coffee+milk & 4: coffee+milk+sugar & 000 \\
3 & coffee+sugar & 0: idle & 7: make coffee+sugar & 000 \\
4 & coffee+milk+sugar & 0: idle & 8: make coffee+milk+sugar & 000 \\
\hline
 & & \multicolumn{2}{l|}{\textbf{ready}} & \\
\hline
5 & make coffee & \multicolumn{2}{l|}{0: idle} & 001 \\
6 & make coffee+milk & \multicolumn{2}{l|}{0: idle} & 011 \\
7 & make coffee+sugar & \multicolumn{2}{l|}{0: idle} & 101 \\
8 & make coffee+milk+sugar & \multicolumn{2}{l|}{0: idle} & 111 \\
\hline
\end{tabular}}
\end{center}
\bi
	\ite output bits: bit 0 = coffee, bit 1 = milk, bit 2 = sugar
	\ite inputs not listed in a row are ignored: the state stays the same
	\ite a table like this is the best check for completeness: every state $\times$ every input
\ei
\os{\newpage}

\item[{\rot\bf C: states, outputs and inputs}]~\\[-\lstskip]
\begin{lstlisting}[language=C]
// the FSM states
enum {
  FSM_STATE_IDLE, FSM_STATE_COFFEE, FSM_STATE_COFFEE_MILK,
  FSM_STATE_COFFEE_SUGAR, FSM_STATE_COFFEE_MILK_SUGAR,
  FSM_STATE_MAKE_COFFEE, FSM_STATE_MAKE_COFFEE_MILK,
  FSM_STATE_MAKE_COFFEE_SUGAR, FSM_STATE_MAKE_COFFEE_MILK_SUGAR,
  NUM_FSM_STATES
};
// the FSM outputs, one per state (Moore machine)
// bit0: add coffee, bit1: add milk, bit2: add sugar
const uint8_t fsm_output[NUM_FSM_STATES] = {0, 0, 0, 0, 0, 1, 3, 5, 7};

// the FSM inputs
enum { FSM_INP_NONE = 0, FSM_INP_LEFT, FSM_INP_RIGHT, FSM_INP_READY };

int fsm_state = FSM_STATE_IDLE;
\end{lstlisting}
\bi
	\ite always use enums for states, inputs and outputs: readable names, and \texttt{NUM\_FSM\_STATES} sizes the table automatically
	\ite define the initial state explicitly
\ei
\os{\newpage}

\item[{\rot\bf C: the transition function}]~\\[-\lstskip]
\begin{lstlisting}[language=C]
int fsm_tic(int fsm_inp) {        // called periodically, every 50 ms
  switch (fsm_state) {
  case FSM_STATE_IDLE:
    if (fsm_inp == FSM_INP_LEFT) fsm_state = FSM_STATE_COFFEE_MILK;
    if (fsm_inp == FSM_INP_RIGHT) fsm_state = FSM_STATE_COFFEE;
    break;
  /* ... COFFEE, COFFEE_MILK, COFFEE_SUGAR, COFFEE_MILK_SUGAR: same pattern ... */
  case FSM_STATE_MAKE_COFFEE:        // wait until the coffee is ready
  case FSM_STATE_MAKE_COFFEE_MILK:
  case FSM_STATE_MAKE_COFFEE_SUGAR:
  case FSM_STATE_MAKE_COFFEE_MILK_SUGAR:
    if (fsm_inp == FSM_INP_READY) fsm_state = FSM_STATE_IDLE;
    break;
  default:
    fsm_state = FSM_STATE_IDLE;      // invalid state: back to a safe state
  }
  return fsm_output[fsm_state];      // Moore FSM: one output per state
}
\end{lstlisting}
\bi
	\ite the period defines the response time; sampling the buttons every 50\,ms also filters the contact bounce
\ei
\os{\newpage}

\item[{\rot\bf Rust: the same machine with enum and match}]~\\[-\lstskip]
\begin{lstlisting}[language=Rust]
pub enum State { Idle, Coffee, CoffeeMilk, CoffeeSugar, CoffeeMilkSugar,
                 MakeCoffee, MakeCoffeeMilk, MakeCoffeeSugar, MakeCoffeeMilkSugar }
pub enum Input { Left, Right, Ready }

impl State {
    pub fn next(self, input: Input) -> State {
        use {Input::*, State::*};
        match (self, input) {
            (Idle, Left) => CoffeeMilk,
            (Idle, Right) => Coffee,
            (Coffee, Left) => MakeCoffee,
            (Coffee, Right) => CoffeeSugar,
            (CoffeeMilk, Left) => MakeCoffeeMilk,
            (CoffeeMilk, Right) => CoffeeMilkSugar,
            (CoffeeSugar, Left) | (CoffeeMilkSugar, Left) => Idle,
            (CoffeeSugar, Right) => MakeCoffeeSugar,
            (CoffeeMilkSugar, Right) => MakeCoffeeMilkSugar,
            (MakeCoffee | MakeCoffeeMilk | MakeCoffeeSugar | MakeCoffeeMilkSugar, Ready) => Idle,
            (state, _) => state, // all other inputs are ignored
        }
    }
}
\end{lstlisting}
\bi
	\ite a \texttt{State} can only hold these values -- no ``invalid state'' as with an \texttt{int}
\ei
\os{\newpage}

\item[{\rot\bf Rust: output function and tests}]~\\[-\lstskip]
\begin{lstlisting}[language=Rust]
pub fn output(self) -> Output {
    let (coffee, milk, sugar) = match self {
        State::Idle | State::Coffee | State::CoffeeMilk
        | State::CoffeeSugar | State::CoffeeMilkSugar => (false, false, false),
        State::MakeCoffee => (true, false, false),
        State::MakeCoffeeMilk => (true, true, false),
        State::MakeCoffeeSugar => (true, false, true),
        State::MakeCoffeeMilkSugar => (true, true, true),
    };
    Output { coffee, milk, sugar }
}

#[test]
fn coffee_with_everything() {
    let s = run(&[Left, Right, Right]);
    assert_eq!(s, MakeCoffeeMilkSugar);
    assert_eq!(s.output(), Output { coffee: true, milk: true, sugar: true });
}
\end{lstlisting}
\bi
	\ite no wildcard in \texttt{output()}: if a state is added later, the compiler reports every \texttt{match} that does not handle it
	\ite the library has no hardware access: \texttt{cargo test} on the PC, the same code on the Pico
\ei
\os{\newpage}

\item[{\rot\bf Recipe for a Moore state machine}]~\\[-\lblskip]
\bi
	\ite analyse the problem before coding: draw the state diagram, write the transition table
	\ite use enums to encode states, inputs and outputs in a readable form
	\ite define the outputs with a suitable encoding, e.g.\ as bit fields
	\ite implement a periodically called tick function (or an event handler) for transitions and outputs
	\ite handle invalid states and unexpected inputs explicitly
	\ite test the transition function separately from the hardware
	\ite our example, tested in Wokwi (C and Rust): left, right, right $\rightarrow$ all three LEDs on; ready $\rightarrow$ all off
\ei
\os{\newpage}

\item[{\rot\bf Tools for state machines}]~\\[-\lblskip]
\bi
	\ite drawing, in the browser
	\bi
		\ite diagrams.net (draw.io), free: \url{https://app.diagrams.net/}
		\ite Visual Paradigm Online (free version available): UML state machine diagrams
	\ei
	\ite text-based diagrams that live in the repository next to the code: PlantUML, Mermaid (\url{https://mermaid.live/})
	\ite simulation of automata in the browser: \url{http://ivanzuzak.info/noam/webapps/fsm_simulator/}
	\ite modelling and simulation
	\bi
		\ite OpenModelica, library \texttt{Modelica.StateGraph} -- free, good for co-simulation with physical models (chapter Cyber-Physical Systems)
		\ite MATLAB/Simulink with Stateflow -- commercial, code generation, widely used in automotive

	\ei
\ei

\end{description}

\section{Activity Oriented Models}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\nsl{Activity oriented models describe what happens to the data and in
which order. Data flow graphs show the dependencies between operations and
leave the order open, which is ideal for signal processing and for deciding
which operations can run in parallel. Flow charts add control flow.
Sequence charts show the communication between components over time.}

\bi
	\ite modelling the flow of data in an embedded system \pr \textbf{DFG} (\underline{d}ata \underline{f}low \underline{g}raph)
	\ite nodes are operations; special nodes for input, output and memory
	\ite edges show the data dependencies on all levels of abstraction
	\ite well suited for the specification and as input for scheduling, because no order is fixed beyond the dependencies
	\ite DFGs can be hierarchical
\ei

     \begin{center}

	  \caption{Data flow graph}

\bi
	\ite extension of a DFG with control flow \pr \textbf{CFG} (control flow graph)
	\ite additional control elements (decisions, loops)
	\ite edges transfer the control
	\ite CFGs are drawn as flow charts
\ei

\begin{description}
\item[{\rot\bf Message Sequence Charts (MSC)}]~\\[-\lblskip]
\bi
	\ite modelling of timing and of the communication between components
	\ite graphical representation of schedules
	\bi
		\ite time is a separate axis (vertical): timing is visible explicitly
		\ite components (activities) on the horizontal axis
	\ei
	\ite today usually drawn as UML sequence diagrams -- the TCP handshake and the DHCP diagram in chapter Networking are examples
\ei

\begin{figure}[!hbtp]
     \begin{center}
	  \epsfig{file=figures/Fig_2_14_MSG,width=1.0\textwidth}\\

     \end{center}

\os{\newpage}

\bi
	\ite \textbf{advantages of activity oriented models}
	\bi
		\ite well suited to visualise schedules and communication
		\ite DFG and CFG can be hierarchical
	\ei
	\ite \textbf{disadvantages}
	\bi
		\ite an MSC shows one scenario only, not all possible behaviours
		\ite no description of non-functional behaviour
		\ite no description of the structure (MSC)
	\ei
\ei
\end{description}

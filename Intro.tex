\nsl{Most computers are not on a desk. They are built into washing machines,
cars, heating systems, medical devices and smartphones, and they control
these devices without the user ever noticing that a computer is involved.
Such embedded systems have their own requirements. They must react in time,
work for years without a reset, run on a battery, cost a few euros at most,
and they must never endanger anybody.
\newline
This lecture covers the whole path from the requirements to a working
device. It starts with models and cyber-physical systems, continues with
processors and their programming in assembly, C, Rust and MicroPython, then
treats the peripherals and interfaces of a microcontroller, networking and
real-time operating systems. All examples run in the browser-based simulator
Wokwi or on Replit, so they can be tried without any hardware.
\newpage}

\section{What is an Embedded System?}
%==============================================================================
\begin{description}
\item[{\rot\bf Definition}]~\\
\defn{def:embedded system intro}
{An \textbf{embedded system} is a computer system that is part of a larger technical system and performs dedicated functions in it -- usually with requirements on timing, energy, reliability and cost.}
\bi
	\ite the user sees the device (a car, a coffee machine), not the computer in it
	\ite interaction with the environment through \textbf{sensors} and \textbf{actuators}, often without a screen or keyboard
	\ite the software is fixed for the purpose (``firmware''), updates are rare and must be safe
\ei
\os{\newpage}

\item[{\rot\bf Embedded systems are everywhere}]~\\[-\lblskip]
\bi
	\ite tens of billions of microcontrollers are produced every year -- many times more than PC and server processors
	\ite a modern car contains 70 to over 100 control units (engine, brakes, airbag, lights, seats, infotainment)
	\ite household: washing machine, heating, smart meter, router, TV, smart speaker
	\ite industry: programmable logic controllers, robots, drives, sensors with network interfaces
	\ite medicine: pacemakers, insulin pumps, ventilators
	\ite communication: smartphones (several processors), base stations, satellites
\ei
\os{\newpage}

\item[{\rot\bf A first example: a coffee machine in the simulator}]~\\[-\lstskip]
\begin{lstlisting}[language=C]
void loop() {
  float t = readTemperature();                      // sensor: 10 mV per degC on A0
  if (t < 91.0) digitalWrite(PIN_HEATER, HIGH);     // actuator: two-point control
  if (t > 94.0) digitalWrite(PIN_HEATER, LOW);
  bool ready = t >= 90.0 && !brewing;
  digitalWrite(PIN_READY, ready);                   // user interface
  if (digitalRead(PIN_BUTTON) == LOW && ready) {    // "make coffee"
    brewing = true;  brewStart = millis();  digitalWrite(PIN_PUMP, HIGH);
  }
  if (brewing && millis() - brewStart >= 20000) {   // 20 s = one cup
    brewing = false;  digitalWrite(PIN_PUMP, LOW);
  }
}
\end{lstlisting}
\bi
	\ite the \textbf{device} is simulated as well: a Wokwi \textbf{custom chip} with a physical model of the boiler, $m c\,\dot T = P_{heater} - k\,(T - T_{room}) - \dot m_{pump}\,c\,(T - T_{room})$
	\ite the program knows the machine only through pins -- like the real one
	\ite Arduino Uno, runs in the browser: \texttt{examples/intro/coffee}
\ei

\section{Characteristics of Embedded Systems}
%==============================================================================
\begin{description}
\item[{\rot\bf Dependability}]~\\[-\lblskip]
\bi
	\ite \textbf{reliability}: probability that the system works correctly for a given time, provided it worked at the start
	\bi
		\ite operation for years without restart; recovery from errors by itself (watchdog)
	\ei
	\ite \textbf{maintainability}: how quickly the system works again after an error
	\ite \textbf{availability}: probability that the system works at a given time
	\ite \textbf{safety}: the system does not endanger people or the environment -- even if it fails
	\ite \textbf{security}: the system resists attacks; connected devices must be protected and updatable
\ei
\qbox{Even perfectly designed systems can fail if the assumptions about the workload and possible errors turn out to be wrong.
\newline
Dependability must be considered from the very beginning -- it cannot be added afterwards.}
\os{\newpage}

\item[{\rot\bf Efficiency}]~\\[-\lblskip]
\bi
	\ite \textbf{energy}: battery operation for months or years, sleep modes, energy harvesting
	\ite \textbf{code size and memory}: kilobytes instead of gigabytes; no hard disk
	\ite \textbf{run time}: real-time requirements -- a correct answer that arrives too late is wrong
	\ite \textbf{size and weight}: the electronics must fit into the device
	\ite \textbf{cost}: in a series of millions every cent counts; the development costs are spread over the number of devices
\ei
\os{\newpage}

\item[{\rot\bf Further characteristics}]~\\[-\lblskip]
\bi
	\ite \textbf{reactive}: continuous interaction with the environment, at its pace (chapter Modelling)
	\ite \textbf{real time}: deadlines are part of the specification (chapter Operating Systems)
	\ite \textbf{dedicated}: one purpose, known in advance -- hardware and software can be optimised for it
	\ite \textbf{heterogeneous}: hardware and software, analog and digital, different processors and networks in one system
	\ite \textbf{long lifetime}: industrial devices and cars are used for 10 to 20 years -- software must be maintained that long
	\ite \textbf{cyber-physical}: computation and physics are coupled in feedback loops (chapter Cyber-Physical Systems)
\ei
\os{\newpage}
\end{description}

\section{Software Development and AI}
%==============================================================================
\nsl{AI tools write code. Since 2021 they have gone from completing the
current line to working on whole projects: they edit several files, run the
compiler and repair their own mistakes. Most developers use them today, and
so did we when we revised this lecture.
\newline
Two questions follow for an embedded systems course. What changes in the
daily work? And what does an engineer still need to know when a machine
writes much of the code? The studies disagree on how much time AI saves.
Some measured faster delivery, one controlled experiment measured the
opposite. On the second question they are clearer. The generated code is
often almost right, and the last errors are found by people who understand
the hardware, read the datasheet, write tests and know how to debug. We
found the same while preparing this lecture. So it still teaches these
things in detail, with or without AI.
\newline
The job market reacts as well. Employers now expect graduates to work with
AI tools as a matter of course, and they pay more for these skills. At the
same time there are fewer of the simple entry-level tasks that used to train
beginners, so new engineers have to judge, test and debug earlier in their
career. The second half of this section collects current figures and the
skills that job advertisements ask for.
\newpage}

\begin{description}
\item[{\rot\bf From code completion to agents}]~\\[-\lblskip]
\bi
	\ite \textbf{code completion} (e.g.\ GitHub Copilot, 2021): the tool proposes the next lines while you type
	\ite \textbf{chat assistants} (since 2022): questions in natural language, explanations, code snippets to copy
	\ite \textbf{agents} (since about 2025, e.g.\ Claude Code, Copilot agent mode, Cursor, OpenAI Codex): the tool reads the repository, changes several files, runs compiler and tests and repairs its own mistakes
	\ite ``vibe coding'' (A.\ Karpathy, 2025): accept generated code without reading it; fine for a throw-away prototype, not for a product
	\ite the developer types less and reviews, tests and decides more
\ei
\os{\newpage}

\item[{\rot\bf How a language model writes code}]~\\[-\lblskip]
\bi
	\ite a large language model continues a text with the most probable next words, learned from huge amounts of public code and documentation
	\ite good at frequent patterns: boilerplate, explanations of code, translation between C and Rust, test cases, summaries of documentation
	\ite weak at
	\bi
		\ite rare or new things: a specific chip variant, the latest version of a HAL, an erratum in the datasheet
		\ite things that are not visible in the code: timing, electrical limits, the state of the hardware
		\ite it cannot tell when it is wrong; an invented function or register looks just as convincing as a real one (``hallucination'')
	\ei
	\ite the answer is only as good as the context: give it the datasheet section, the existing code, the exact error message and the tool versions
\ei
\os{\newpage}

\item[{\rot\bf What studies show}]~\\[-\lblskip]
\begin{center}
\resizebox{0.95\textwidth}{!}{%
\begin{tabular}{|l|l|}
\hline
\textbf{study} & \textbf{finding} \\
\hline
Stack Overflow 2025 \cite{so2025} & 84\,\% use or plan to use AI tools \\
49\,000 developers & 46\,\% distrust the accuracy; 45\,\% find debugging AI code slow \\
\hline
DORA 2025 \cite{dora2025} & 90\,\% use AI at work; more changes delivered, \\
5\,000 professionals & but delivery is less stable; AI amplifies a team's habits \\
\hline
METR 2025 \cite{metr2025} & experienced developers 19\,\% \textbf{slower} with AI, \\
randomised trial & although they felt 20\,\% faster; 2026: probably faster, uncertain \cite{metr2026} \\
\hline
Veracode 2025 \cite{veracode2025} & 45\,\% of generated code samples had security flaws \\
\hline
Anthropic 2026 \cite{anthropic2026skills} & learning with AI: 50\,\% in a test without AI, \\
randomised, 52 people & without AI: 67\,\%; largest gap in \textbf{debugging} \\
\hline
\end{tabular}}
\end{center}
\bi
	\ite feeling faster is not being faster; measure it
\ei
\os{\newpage}

\item[{\rot\bf AI in embedded systems}]~\\[-\lblskip]
\bi
	\ite embedded code depends on details that are rare in the training data: chip variants, register maps, SDK versions, wiring
	\ite benchmark with 27 language models on the ESP32 \cite{babiuch2026}
	\bi
		\ite simple sensor applications: 19 to 23 models delivered working code
		\ite complex applications (sensor, cloud database, dashboard): only 3 to 5 models
		\ite most frequent failure: libraries and functions that do not exist, or wrong use of real APIs
	\ei
	\ite benchmark EmbedAgent (Raspberry Pi Pico, ESP32, Arduino, 126 tasks) \cite{xu2026embedagent}: the best model solved about 56\,\% of the tasks; porting code from Arduino to ESP-IDF succeeded in fewer than 30\,\% of the cases
	\ite many errors show up only on the hardware or under real timing; that the compiler accepts the code proves little
\ei
\os{\newpage}

\item[{\rot\bf Experience from preparing this lecture}]~\\[-\lblskip]
\bi
	\ite we wrote the examples of this lecture with an AI assistant, then compiled each of them and ran it in the Wokwi simulator
	\ite the tests found errors in code that compiled without warnings, for example
	\bi
		\ite a FreeRTOS demo that could not show the race condition at all, because the first task finished before the second one was created (chapter Operating Systems)
		\ite an MQTT client that the public test broker sometimes rejected, because a packet was sent in two TCP segments (chapter Networking)
		\ite a PWM calculation that assumed a 125\,MHz system clock, while the Arduino core runs the RP2040 at 200\,MHz
		\ite a delay that took 4\,$\mu$s instead of 1\,ms in the simulator; the debugger and a measurement found it (chapter Programming)
	\ei
	\ite to find them we needed to know how the scheduler starts tasks, how TCP splits data and how the clocks are configured, plus one long debugging session; tests that check the behaviour caught what the compiler could not
\ei
\os{\newpage}

\item[{\rot\bf How the development environment changes}]~\\[-\lblskip]
\bi
	\ite more code is \textbf{read and reviewed} than written by hand
	\ite specifications, interface descriptions and test cases become the input for the AI, so precise requirements pay off twice
	\ite automatic checks become more important: compiler warnings, static analysis, unit tests, simulation (Wokwi), continuous integration
	\ite projects are organised so that tools find the context: clear structure, documented interfaces, README files
	\ite the engineer stays responsible: safety standards (IEC 61508, ISO 26262) require traceable requirements, reviews and tests, no matter who or what wrote the code
	\ite new questions: confidentiality (company code in external services), licenses of generated code, reproducibility
\ei
\os{\newpage}

\item[{\rot\bf AI and the job market}]~\\[-\lblskip]
\begin{center}
\resizebox{0.95\textwidth}{!}{%
\begin{tabular}{|l|l|}
\hline
\textbf{source} & \textbf{finding} \\
\hline
WEF Future of Jobs 2025 \cite{wef2025} & AI and big data are the fastest-growing skills, \\
1\,000 employers, 55 economies & followed by networks and cybersecurity; 39\,\% of core skills change by 2030 \\
\hline
PwC AI Jobs Barometer 2026 \cite{pwc2026} & jobs with AI skills pay on average 62\,\% more; \\
over 1 billion job ads & US entry jobs exposed to AI ask 7 times more often for senior skills \\
\hline
Stanford, ``Canaries'' 2026 \cite{brynjolfsson2026} & age 22--25 in AI-exposed jobs: employment 19\,\% below less-exposed peers; \\
US payroll data & fewer hires, no gap for experienced staff; no general job loss \\
\hline
Bitkom 2026 \cite{bitkom2026} & 79\,000 open IT positions in Germany (2023: 149\,000); \\
602 companies & 63\,\% expect AI skills in \textbf{all} IT jobs; 55\,\% expect classical entry tasks to disappear \\
\hline
\end{tabular}}
\end{center}
\bi
	\ite AI shifts the work more than it removes it: jobs where AI assists people grow, jobs where it replaces routine tasks hire fewer beginners
\ei
\os{\newpage}

\item[{\rot\bf What employers ask for}]~\\[-\lblskip]
\bi
	\ite working with AI tools is a basic requirement, not a speciality: giving context, splitting tasks, reviewing and testing the result
	\ite judgment from the first day: beginners do less routine work and more checking, integrating and deciding
	\ite governance: 74\,\% of the companies in the Bitkom survey expect steering and controlling AI to become more important \cite{bitkom2026}
	\ite AI literacy is a legal duty: since 02/2025 the EU AI Act (Art.\,4) requires employers to train staff who use AI, supervised since 08/2026 \cite{euaiact}
	\ite in embedded systems in particular
	\bi
		\ite security and update processes: the EU Cyber Resilience Act requires vulnerability reporting since 09/2026 (chapter Networking)
		\ite edge AI: running small neural networks on microcontrollers (TensorFlow Lite Micro, quantisation, memory and timing budgets)
		\ite functional safety: traceable requirements and tests, also for generated code
	\ei
	\ite and still: analytical thinking, which 7 of 10 employers in the WEF survey call the most important core skill \cite{wef2025}
\ei
\os{\newpage}

\item[{\rot\bf Preparing for your career}]~\\[-\lblskip]
\bi
	\ite learn the basics so well that you notice when the AI is wrong; this is what distinguishes you from the tool
	\ite build projects that you can explain in an interview line by line, including the bugs you found
	\ite show that you can verify: tests, simulation, measurements, reviews
	\ite learn one agentic tool properly, including its limits, and the rules of your employer on confidential code
	\ite keep learning: 61\,\% of the companies expect more pressure on IT staff to train continuously \cite{bitkom2026}
\ei
\os{\newpage}

\item[{\rot\bf What you still need to know}]~\\[-\lblskip]
\bi
	\ite computer architecture, memory, interrupts and concurrency: without them you cannot tell wrong code from right code
	\ite reading datasheets and reference manuals, the only reliable source for registers, timing and electrical limits
	\ite specifying a problem so clearly that a colleague, or an AI, can solve it: requirements, state machines, interfaces
	\ite reading code critically; you commit only what you understand
	\ite testing: designing tests, simulating, measuring, and knowing when something is really done
	\ite debugging with debugger and logic analyzer, step by step; this was the largest gap in the Anthropic study
	\ite asking what happens if the system fails or is attacked
	\ite seeing hardware, software and physics as one system
	\ite explaining and documenting decisions for the team
\ei
\os{\newpage}

\item[{\rot\bf Using AI well in this course}]~\\[-\lblskip]
\bi
	\ite try it yourself first; you learn while you struggle with a problem
	\ite ask why, not just how: in the Anthropic study, learners who asked conceptual questions and fixed their errors themselves learned the most
	\ite give context: chip, board, SDK version, the relevant datasheet section, the complete error message
	\ite check every API and register against the documentation
	\ite never hand in or commit code that you cannot explain
	\ite test in Wokwi or on the hardware; ``it compiles'' does not mean ``it works''
	\ite follow the rules of the course and your employer on AI use, and state where AI was used
\ei
\os{\newpage}

\item[{\rot\bf Exercises}]~\\[-\lblskip]
\bi
	\ite Let an AI assistant write the debouncing example of chapter Peripherals and Interfaces in C. Review the code, run it in Wokwi with a bouncing button and list all problems you find.
	\ite Ask an AI for the address of the register \texttt{GPIO\_OUT\_XOR} of the RP2040 and for the meaning of its bits. Check the answer in the datasheet.
	\ite Solve one exercise of chapter Programming without AI and one with AI. Compare time, result and what you can explain afterwards.
	\ite Read five current job advertisements for embedded software engineers. List which AI-related skills they ask for and which of them this lecture covers.
\ei
\os{\newpage}
\end{description}
